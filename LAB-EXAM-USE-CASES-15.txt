
# USE CASE 1: Web Server HTTP Status Code Analysis
// 1. Problem Statement

A company maintains millions of web-server access logs in HDFS. The data engineering team wants to analyze the logs and determine how many requests were received for each HTTP status code.

//For example:
200 → Successful request
404 → Page not found
500 → Server error

The MapReduce program should:

1. Read web-server logs from HDFS.
2. Extract the HTTP status code.
3. Generate (status_code, 1) from the Mapper.
4. Use a Combiner for local aggregation.
5. Use a custom Partitioner to distribute status codes among Reducers.
6. Shuffle and group(sort) identical status codes.
7. Use the Reducer to calculate the final count.
8. Store the result in HDFS.


2. Sample Input


web_logs.txt

//
192.168.1.10 GET /home 200
192.168.1.11 GET /login 200
192.168.1.12 GET /product 404
192.168.1.13 GET /home 200
192.168.1.14 GET /checkout 500
192.168.1.15 GET /product 404
192.168.1.16 GET /home 200
192.168.1.17 GET /server 500



3. Expected Output
200    4
404    2
500    2

//Meaning:

HTTP 200 → 4 requests
HTTP 404 → 2 requests
HTTP 500 → 2 requests

6. Map Stage

The Mapper reads:
192.168.1.10 GET /home 200

and generates:

200    1

Another record:

192.168.1.12 GET /product 404
generates:

404    1

So Mapper output could be:
200    1
200    1
404    1
200    1
500    1
404    1
200    1
500    1

7. Combiner Stage

The Combiner performs local aggregation.

For example, if one Mapper produces:

200    1
200    1
200    1
404    1

the Combiner can produce:

200    3
404    1

This reduces the amount of intermediate data transferred over the network.


// Interview point

> Combiner is a local mini-reducer. It reduces intermediate data before it is transferred to Reducers.

//Important:

Combiner is optional. Hadoop does not guarantee that it will execute.

8. Partitioner Stage

The Partitioner decides which Reducer receives each key.

//For example:

200 → Reducer 0
404 → Reducer 1
500 → Reducer 1


The important rule is:

> All values belonging to the same key must go to the same Reducer.

For example, all 200 records must reach the same Reducer.


9. Shuffle and Sort

Hadoop groups the values belonging to the same key.

//Conceptually:
200 → [1,1,1,1]
404 → [1,1]
500 → [1,1]

After Combiner, the amount of data transferred may already be reduced.


10. Reduce Stage

Reducer receives:
200 → [1,1,1,1]
404 → [1,1]
500 → [1,1]

and calculates:
200 → 4
404 → 2
500 → 2

//Final HDFS output:
200    4
404    2
500    2

# Important Interview Questions
Q1. Why do we use Combiner?

Answer:

> Combiner performs local aggregation at the Mapper side and reduces the amount of intermediate data transferred across the network during Shuffle.

 Q2. Is Combiner mandatory?

Answer:

> No. Combiner is optional and Hadoop may or may not execute it.

 Q3. What does Partitioner do?

Answer:

> Partitioner determines which Reducer receives a particular key.

 Q4. What is the most important rule of Partitioner?

Answer:

> All records with the same key must be sent to the same Reducer.

 Q5. What happens during Shuffle?

Answer:

> Hadoop transfers, sorts and groups Mapper output based on keys before sending the grouped data to the Reducer.

 Q6. Why use Java Mapper?

> Java provides native Hadoop MapReduce APIs and is traditionally used for Hadoop MapReduce applications.

 Q7. Why use Python Mapper?

> Python can be used with Hadoop Streaming, allowing Python programs to participate in the MapReduce framework through standard input and output.

 Q8. What is the difference between Combiner and Reducer?
Combiner → local aggregation → optimization
Reducer  → final aggregation → final result


 Q9. Does Partitioner aggregate data?

> No. Partitioner only determines which Reducer receives a key.

 Q10. What happens if the Partitioner sends the same key to different Reducers?

> The aggregation can be split across Reducers, so the final result for that key would not be correctly combined. Therefore, the same key must always go to the same Reducer.
